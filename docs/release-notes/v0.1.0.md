# Hatua v0.1.0

The first published release of Hatua, an embeddable workflow designer. A Host drags Steps
together, maps one Step's typed outputs into the next, branches and loops, and reads and writes
the resulting Workflow Definition as plain YAML. Hatua never executes anything itself.

Nine `@hatua/*` packages and one Go module publish at this version together.

## Supported surfaces

Two packages are the supported API:

- **`@hatua/react`** — the designer a Host embeds in a browser: components, hooks and theming.
- **`@hatua/sdk`** — the Node-side contract plus the shared expression evaluator, for a runner
  that needs to parse the same YAML and evaluate the same Expressions the designer wrote.

`@hatua/document`, `@hatua/expressions`, `@hatua/layout`, `@hatua/log`, `@hatua/model`,
`@hatua/schema` and `@hatua/services` are also on npm, but only because `@hatua/react`'s build
treats them as externals rather than bundling them. They are implementation details, not a
supported API — nobody installs `@hatua/model` directly and expects a contract.

## Stability

`@hatua/react` is 0.x and still moving. While it stays 0.x, a breaking change can land on a minor
version bump, so semver alone does not protect a Host that upgrades freely — pin an exact version
and read release notes before upgrading.

Theming has a known gap: `@hatua/react` styles ship per component rather than as a stylesheet a
Host imports, and the plain-stylesheet escape hatch (`@hatua/react/styles.css`) described for that
approach is deferred, not shipped. A Host that needs to override styles beyond what
`createTheme()` reaches does not have a supported way to do it yet.

## Install

```sh
npm install @hatua/react react react-dom
```

```sh
npm install @hatua/sdk
```

```sh
go get hatua.dev/go@v0.1.0
```

## Versioning

All nine `@hatua/*` packages and the Go module share one version. A tag sets the same version
everywhere; the packages are not versioned independently.
